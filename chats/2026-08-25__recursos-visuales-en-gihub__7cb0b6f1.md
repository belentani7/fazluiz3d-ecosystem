A continuación, se detalla el inventario máximo y confirmado de todos los recursos, herramientas y formatos visuales disponibles de forma nativa en el ecosistema de GitHub, clasificados por su función técnica y operativa.

### 1. Diagramas y Gráficos Nativos en Markdown
GitHub soporta la renderización directa en su motor de Markdown (utilizable en `README.md`, Issues, Pull Requests, Wikis y Discussions) de múltiples lenguajes de modelado visual, eliminando la necesidad de subir imágenes estáticas.
*   **Mermaid:** Permite la generación mediante texto de diagramas de flujo, diagramas de secuencia, gráficos de Gantt, diagramas de clase, diagramas de estado y gráficos circulares [[1]].
*   **GeoJSON y TopoJSON:** Renderiza mapas geoespaciales interactivos directamente en el repositorio, permitiendo trazar rutas, polígonos y marcadores de ubicación [[37]].
*   **Modelos 3D (ASCII STL):** Incluye un visor tridimensional interactivo que permite rotar y hacer zoom sobre archivos de modelos 3D o piezas de impresión sin salir del navegador [[35]].

### 2. Herramientas de Comparación Visual (Image Diffing)
Para el control de versiones de activos gráficos (PNG, JPG, GIF), GitHub integra un visor de diferencias visuales avanzado al comparar commits.
*   **2-up:** Visualización estática lado a lado de la versión base y la versión modificada.
*   **Swipe (Deslizar):** Herramienta interactiva con una barra deslizante para comparar ambas imágenes en el mismo eje espacial.
*   **Onion Skin (Piel de cebolla):** Superposición de imágenes con opacidad regulable para detectar alteraciones milimétricas en el diseño [[25]].
*   **Diff Highlights / Pixel Strip:** Aislamiento y recuadro en rojo de los píxeles exactos que han sido modificados, eliminados o añadidos.

### 3. Gestión Visual de Proyectos (GitHub Projects)
El módulo de planificación permite estructurar el trabajo mediante vistas visuales adaptables que se sincronizan en tiempo real con el código y las incidencias [[17]].
*   **Tableros Kanban (Board):** Organización visual de tareas en columnas de estado para metodologías ágiles.
*   **Vista de Tabla (Table):** Formato de hoja de cálculo para la edición masiva de metadatos, etiquetas y prioridades.
*   **Roadmaps (Hojas de ruta):** Diagramas de Gantt nativos que estructuran cronogramas, dependencias de tareas e iteraciones a lo largo del tiempo [[20]].

### 4. Temas de Accesibilidad e Interfaz (UI)
GitHub dispone de un motor de renderizado de interfaz con opciones exhaustivas para reducir la fatiga visual y garantizar la accesibilidad.
*   **Temas para Daltonismo:** Incluye configuraciones específicas para *Protanopia* y *Deuteranopia* (ceguera al rojo/verde) que ajustan los indicadores de estado de los Pull Requests y las notificaciones [[44]]. También cuenta con soporte para *Tritanopia* (ceguera al azul/amarillo).
*   **Alto Contraste:** Temas con bordes marcados y tipografía optimizada para usuarios con baja visión, tanto en modo claro como oscuro.
*   **Modo Oscuro Automático:** Sincronización visual con los parámetros nativos del sistema operativo del usuario.

### 5. Analítica y Estadísticas Visuales (Insights)
La pestaña "Insights" de los repositorios agrupa herramientas de minería de datos visual para auditar la salud del proyecto.
*   **Network Graph:** Un árbol visual e interactivo que traza el historial de commits, bifurcaciones (forks) y uniones (merges) de todas las ramas.
*   **Code Frequency:** Gráficos de barras que desglosan visualmente las adiciones (verde) y eliminaciones (rojo) de líneas de código por semana.
*   **Contributors Graph:** Mapa de calor histórico que detalla el volumen de commits por usuario a lo largo de la vida del repositorio.
*   **Cuadrícula de Contribuciones:** El calendario visual del perfil de usuario que muestra la frecuencia de actividad diaria mediante una escala de intensidad de color verde.

### 6. Widgets Dinámicos para Perfiles (Profile README)
Mediante el repositorio especial con el nombre del usuario, GitHub permite la integración de recursos visuales dinámicos generados por servidores externos o GitHub Actions.
*   **GitHub Readme Stats:** Tarjetas en formato SVG que se actualizan solas para mostrar estadísticas de commits, lenguajes más utilizados y rachas de actividad [[53]].
*   **Badges (Insignias):** Soporte nativo para escudos dinámicos (vía Shields.io) que indican visualmente el estado de las compilaciones de CI/CD, licencias o versiones de paquetes.
*   **Widgets de Terceros:** Integración visual de reproducciones actuales de Spotify, animaciones de escritura o contadores de visitas de perfil.

### 7. Visualización de Pipelines (GitHub Actions)
*   **Gráficos de Flujo de Trabajo:** Representación visual en forma de nodos que muestra cómo se encadenan y bifurcan los distintos *jobs* dentro de un pipeline de automatización.
*   **Matrices de Construcción:** Tableros visuales con indicadores rápidos (checkmarks o cruces) por cada entorno, sistema operativo o versión de lenguaje en el que se ejecuta una acción simultáneamente.

### 8. Previsualización de Archivos de Diseño
A través de Git LFS (Large File Storage) y el visor nativo, GitHub soporta la inspección visual de archivos binarios de diseño.
*   **Renderizado Nativo:** Capacidad de previsualizar capas y composiciones de archivos pesados como PSD (Photoshop) o AI (Illustrator).
*   **Vista previa de PDFs y CSVs:** Renderizado estructurado de documentos y tablas de datos directamente en la interfaz web sin necesidad de descargar el archivo.

## 1. AUDITORÍA TÉCNICA: ERRORES QUE BLOQUEAN EL CÓDIGO DEL ARCHIVO

### 1.1. `frontend/package.json` del MVP Ω-MAX (roto tal como está)
- `"tanstack-query": "^5.62.7"` **no existe** como paquete: el nombre real es `@tanstack/react-query`.
- Falta `axios`, que es usado por `api-client.ts`.
- Falta `next-themes`, usado por `theme-provider.tsx`.
- Falta `@radix-ui/react-dialog`, usado por `dialog.tsx` (solo está `@radix-ui/react-slot`).
- Falta `tailwindcss-animate`, requerido por `tailwind.config.ts`.
- Sobra `@prisma/client` en el frontend (no se usa) y `shadcn-ui` como dependencia (shadcn no es un paquete a instalar: los componentes se copian al repo).
- **Archivos importados pero nunca generados:** `@/lib/utils` (función `cn`), `@/application/services/query-client`, `ui/toast.tsx` y `ui/toaster.tsx` completo. Sin ellos, `npm run dev` falla.

### 1.2. Conflicto Tailwind 3 vs 4 (incompatibilidad real)
El archivo mezcla `tailwindcss: ^4.0.0` en devDependencies con `globals.css` usando `@tailwind base/components/utilities`. Tailwind v4 eliminó las directivas `@tailwind` y se configura con `@import "tailwindcss"` y tokens en CSS [[25]]. La v4 estable salió el 22 de enero de 2025 [[30]]. **Decisión obligatoria:** o fijas `tailwindcss@3.4.x` con esa config, o migras a sintaxis v4. Tal como está, el build de estilos falla.

### 1.3. Conflicto de red en el frontend
`next.config.ts` define rewrites de `/api/*` hacia el backend, pero `api-client.ts` apunta a `NEXT_PUBLIC_API_URL` absoluto (`http://localhost:3001`). En producción eso rompe CORS y expone el backend. Lo correcto: cliente con rutas relativas (`/api/v1/...`) + rewrites de Next como proxy.

### 1.4. Backend y Docker
- `npx prisma migrate deploy` **sin carpeta de migraciones** no aplica nada: usa `prisma db push` o genera migraciones reales.
- El Dockerfile multi-etapa copia `node_modules/.prisma` de forma frágil; lo robusto es ejecutar `npx prisma generate` en la imagen final.
- Kafka con Zookeeper (`cp-zookeeper`) es el modo legacy; el estándar actual es KRaft.
- `sanitizeInput` con regex `/<[^>]*>/g` **no es sanitización real** contra XSS; el referente OWASP es DOMPurify (en servidor: `isomorphic-dompurify`).
- `z.number()` + `valueAsNumber` produce `NaN` con campo vacío y mensajes de error confusos; usa `z.coerce.number()`.

### 1.5. Agente LangGraph
- `StateGraph` con canales Zod depende de la versión; la API estable y documentada es `Annotation`.
- `fromBeginning: true` reprocesa **todo el historial** de `stock.low` en cada reinicio del agente (órdenes duplicadas); debe ser `false` con `groupId` persistente.

### 1.6. Métrica obsoleta en el "Libro del Front-End"
El documento exige `FID < 100ms`. FID fue reemplazado oficialmente por INP como Core Web Vital el 12 de marzo de 2024 [[6]]. El trío correcto y vigente es: **LCP < 2.5s, INP < 200ms, CLS < 0.1**. INP además es señal de ranking en Google [[14]].

## 3. LO QUE FALTA PARA EL MÁXIMO REAL (ausencias críticas del archivo)

1. **CI de calidad en GitHub Actions:** Lighthouse CI (presupuestos de performance/accesibilidad), Playwright (E2E de flujos críticos) y `axe-core` (a11y automatizada) en cada push. Sin esto, "WCAG AA" y "Lighthouse > 90" son deseos, no garantías.
2. **Seguridad HTTP real en Netlify:** `_headers` con `Content-Security-Policy`, `Strict-Transport-Security`, `X-Content-Type-Options: nosniff`, `Referrer-Policy`, `Permissions-Policy`. El archivo menciona CSP pero no lo implementa.
3. **Cumplimiento RGPD en la Lead API:** capturar emails y venderlos "anonimizados" sin base jurídica es alto riesgo legal; el RGPD exige consentimiento explícito, política de privacidad, derecho de supresión, y la anonimización verdadera es la del Considerando 26, no un `delete` de campos. Esto debe rediseñarse antes de monetizar leads.
4. **Offline real:** IndexedDB para datos (cursos, checklist), no solo `localStorage`; Service Worker con estrategia stale-while-revalidate.
5. **i18n profesional:** `Intl.API` para fechas/monedas, `hreflang` en SEO, un JSON por idioma cargado bajo demanda.
6. **SEO verificable:** Search Console, sitemap.xml real, Schema.org `Course`/`EducationalOrganization` validado con Rich Results Test de Google.
7. **Analítica privacy-friendly:** Umami o Plausible en lugar de GA4 si la audiencia es vulnerable (coherente con tu Regla de Ingeniería de no depender de externos).
8. **Canal B2B con entidades reales existentes** (Cáritas, Cruz Roja, CEPA, ayuntamientos) como primer cliente piloto, en lugar de proyecciones abstractas.
